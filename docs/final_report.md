**Report date** 2026-11-08  
**Repository** `catslovefish1/AlphaGo_Trainium`  
**Hardware** AWS Trainium2 `trn2.48xlarge`, 64 logical NeuronCores  
**Framework** PyTorch with the AWS Neuron XLA runtime

## Executive result

The project completed the requested 9×9 compilation, distributed execution,
rules, CPU tree-search, self-play learning, timing, memory-capacity, and
public-engine evaluation probes. The training curve moved in the expected
direction from random initialization. The strongest retrieved checkpoint was
055.

The public KataGo ladder remained at 0/12 wins for checkpoint 055 across 1,
8, and 32 visits. This establishes a measurable learning and evaluation
baseline while leaving the relative-strength target open.

The empirical performance work identified stable batch capacity and measurable
CPU-to-Neuron overlap. An exact HLO MFU percentage is still unavailable because
Neuron Explorer reported `model_flops: 0` for both the policy-value profile and
the explicit matmul validation. The recorded instruction-MFU, HBM, DMA,
tensor-engine, host-transfer, and all-reduce fields remain useful diagnostics.

The trn09 allocation ended at the infrastructure level. No further training or
Slurm submission was performed after the node became unavailable.

### CPU, transfer, tensor-engine, and collective overlap

The fixed-shape tensor overlap probe measured a mean host-to-HBM time of
0.2965 ms, forward time of 3.8071 ms, and sequential step time of 4.5801 ms.
The producer-thread path measured 3.8130 ms, giving a 1.2012× timing proxy and
0.7671 ms of hidden headroom.

The queue-depth probe at per-rank batch 4,096 measured the following whole-node
results.

| Path | Mean step (ms) | Speedup |
| --- | ---: | ---: |
| Sequential | 34.2935 | 1.000× |
| Queue depth 1 | 30.6250 | 1.120× |
| Queue depth 2 | 29.9135 | 1.146× |
| Queue depth 4 | 29.7212 | 1.154× |

Queue depth 2 captured nearly all of the measured benefit with less host
buffering. Exact attribution among CPU launch, HBM movement, tensor-engine
execution, and lazy synchronization requires the Neuron system and device
timeline captured by the exact-MFU job.

### Exact MFU status

Neuron Explorer captured the device and HLO artifacts. The selected summary had
two device records, zero HLO model FLOPs, and zero HLO MFU. It reported nonzero
instruction counts and instruction-level MFU fields. The explicit matmul
validation produced the same metadata limitation under NeuronX 2.26.6360 and
Explorer release 2.31.

The repository parser at `python3 -m alphago.mfu_report` treats zero
`model_flops` as an unresolved exact-MFU gate. This avoids presenting an
instruction proxy as an exact HLO percentage.

## Reproducibility and artifact handling

The clean project is maintained in `AlphaGo_Trainium`. Head01 is used as the
staging and collection point. Nodes pull the code directly from GitHub when a
job is allocated. Checkpoint files remain on head01 under the synchronized
checkpoint directory and are excluded from GitHub.

The final retrieved evidence includes code, readable metrics, profiling
summaries, match JSON, Slurm logs, and the machine-readable goal audit. The
latest local repository also contains offline tests for Go rules, CPU MCTS, MFU
summary parsing, and GTP protocol handling.
